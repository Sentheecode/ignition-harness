# 首轮验证与路线

本文件是研究阶段的验证建议，不是已经执行的测试，也不是排期承诺。

> 用户已明确最终范围涵盖 Tag、脚本、Gateway 配置与数据库等工程操作。此前的单 View 验证仅是连通性检查，不能代表完整 MVP 验收；完整连续场景见 [深入技术调查第 9 节](technical-investigation.md#9-把验证落到用户的完整任务上)。

## 需要的环境

独立开发 Gateway：8.3.9 + 固定版本 Artek-MCP，以及固定 build 的 2027 Beta + Catalyst Core/Agent。配置 Perspective、测试项目、模拟标签与测试身份；记录模块许可和启用状态。无需连接生产设备。

2027 路径另需执行 [Catalyst 专项验证 CAT-01 至 CAT-10](catalyst-research.md#7-catalyst-专项验证清单)，特别验证 Designer 编辑工具是否可从外部 MCP 使用。

## P0：先回答能否闭环

1. 导出两个服务的 MCP initialize、tools/list（含分页）及 schema，移除凭据后保存 fixture。记录 transport、协议版本、身份权限和模块版本。
2. 读取同类 View、Style、脚本和项目配置，确认是否能获得足够信息用于无损往返；保留资源元数据与未知字段。
3. 修改测试 View 的文字或布局，经服务端写入后重读、打开 Perspective 确认生效；再恢复原始快照。分别验证两种适配器，不以其中一个的结果代替另一个。
4. 同时打开 Designer 修改同一资源，验证冲突检测及是否会被覆盖；测试多资源写入中断和补偿失败。
5. 试验 iframe 与桌面浏览器容器：登录跳转、Cookie、WebSocket、TLS、分辨率、会话注销、资源更新和截屏；确认测试结果对应哪个变更集。
6. 覆盖 read-only、权限不足、模块不可用、连接中断与工具 schema 改变，确保不会显示虚假的发布成功。

验收证据：版本清单、脱敏 schema、前后资源快照、差异、调用结果、重读结果及真实会话截图。只存截图不证明资源写入正确。

## P1：最小产品

在 P0 可行后确定 DSH 插件或独立工作台路线，再编写实施规格。实现连接配置、能力显示、资源树、工作副本、AI 修改、差异审查、发布状态和真实预览。

验收场景：给出“修改设备页面中的标题和布局”，用户不进入 Designer 即可完成读取、修改、发布、预览和恢复；没有支持的资源类型必须明确提示。

## P2：扩大 Designer 替代范围

按实际需求增加绑定、事件脚本、Named Query、标签/UDT 与组件属性编辑。每项建立独立能力矩阵与往返样例，然后评估图形化拖拽及团队协作。

## 尚待确认的产品问题

- “替代 Perspective 预览”是否接受工作台内的真实 Gateway 会话，还是要求脱离 Gateway 的离线预览？两者工程规模差异极大。
- 首批最重要的 Designer 工作是什么：Perspective 页面、标签/UDT、脚本还是项目配置？
- 交付形态是桌面应用还是浏览器工作台？是否已有可提供的测试 Gateway？
